# AXIOMA — объяснимое пополнение склада

Прототип HackAlem AI для кейса «Автоматический расчёт заказов поставщикам для пополнения склада» ТОО «Электрокомплект».

Менеджер загружает выгрузки IEK и Systeme Electric, получает рекомендации с объяснением, корректирует количества и утверждает выгрузку. Заказы не отправляются поставщикам автоматически.

## Архитектура

Excel / ZIP / CSV → нормализация кодов 1С и единиц → контроль качества → очистка разовых продаж → восстановление подтверждённого потерянного спроса → сезонный прогноз и тренд → остатки и ожидаемые поступления → рекомендуемый заказ → проверка менеджером → экспорт.

Python, pandas и Streamlit. Расчёт работает локально, без внешнего AI API и личных аккаунтов. AI используется при разработке; алгоритм расчёта воспроизводим и объясним.

## Обязательные функции

- Учёт истории, остатка, товаров в пути, категории и прогноза роста.
- Сезонность и устойчивый тренд спроса.
- Компенсация спроса только при подтверждённых периодах отсутствия товара.
- Выявление разовых крупных операций; поддержка обезличенного клиента при наличии.
- Заказы по поставщикам с объяснением каждой строки.

## Выявленные ограничения входных данных

- 12 файлов Excel, около 249 тысяч строк в двух детализациях продаж.
- В детализации есть дата, документ, код, единица, склад и количество; ID клиента отсутствует. Номер документа не является ID клиента.
- Отрицательные количества требуют отделения возвратов; брать абсолютное значение нельзя.
- Начальный месячный остаток IEK нельзя считать текущим остатком на дату расчёта.
- Месячные остатки не подтверждают точные дни stockout.
- Systeme Electric содержит текущий свободный остаток, категорию, коэффициенты и ожидаемое поступление.
- Сентябрь 2026 неполный. Сравнение полных месяцев исключает его.
- Минимальная партия, кратность и перевод единиц закупки учитываются отдельно.

## Установка и запуск

Требуется Python **3.12**, 4 ГБ свободной памяти для полных исходных архивов, браузер. Интернет нужен для первоначальной установки зависимостей. Внешние ключи, подписки и переменные окружения не требуются.

Windows PowerShell, из папки репозитория:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m streamlit run app.py
```

macOS / Linux:

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m streamlit run app.py
```

Откройте http://localhost:8501. В Windows также можно запустить `start.ps1` из PowerShell, если локальная политика допускает выполнение скриптов. Обход политики не требуется: команды выше эквивалентны.

Docker — дополнительный способ, требует Docker и отдельной проверки в вашей среде:

```bash
docker build -t axioma .
docker run --rm -p 8501:8501 axioma
```

## Реальные архивы партнёра

В боковой панели выберите «Архивы поставщиков» и загрузите **IEK.zip** и **Systeme electric.zip**. Поддерживается исходная структура файлов из кейса. Чтение и расчёт полного набора могут занять несколько минут; результаты кэшируются в локальном процессе.

На первом запуске откройте «Качество данных». Для IEK без актуального остатка рекомендации заблокированы; введите подтверждённый остаток через таблицу параметров. Для отмеченных кабелей укажите перевод складских единиц в единицу закупки и снимите флаг необходимости уточнения. Нельзя предполагать, что любая бухта равна 305 м: в демонстрации это задано явно для одного синтетического товара.

Сроки поставки 14 дней, пересмотр 30 дней, страховой запас 7/10/14 дней — **демонстрационная политика**, а не утверждённые условия поставщиков. Значения редактируются. Категории 1/2/3 отображаются в политику 14/10/7 дней как открытое допущение. Смысл категорий необходимо согласовать с партнёром.

Начальные месячные остатки не подтверждают точные stockout. Данные агрегированы по складам, потому что в переданном наборе нет полного соответствия текущих остатков каждому складу детализации. ID клиента не изобретается из номера документа. Месячные сводки не суммируются с транзакциями: это дало бы двойной счёт. Ранние месяцы до начала дневной детализации дополняют историю для сезонности. Сверка сумм доступна в разделе качества данных; реальные сводки и детализация имеют расхождения. Денежная сезонность не подменяет сезонность количества.

В исходной детализации встречаются старые возвраты при отсутствии обычных продаж за тот же ранний период. Они не создают искусственную многолетнюю историю нулевого спроса: дневной календарь начинается с первой положительной операции. Ранняя месячная сводка используется отдельно. Разовые операции и клиентов в месячных агрегатах проверить нельзя; это ограничение видно в приложении.

Коэффициенты прироста меньше −100% не являются допустимой корректировкой спроса. Если они встречаются в исходной таблице, импорт явно отмечает ошибку и включает автоматический тренд вместо некорректного значения; менеджер должен проверить такую позицию.

## Методология

1. **Возвраты:** отрицательные операции остаются в исходном графике, но не становятся положительным спросом. Их влияние на физический запас должно быть уже отражено в актуальном остатке.
2. **Разовые операции:** суммы по документу/дате и, при наличии, по обезличенному клиенту/дате сравниваются с порогом `max(5 × медиана, медиана + 6 × 1.4826 × MAD, 20)`. Нужно не менее 8 положительных наблюдений. Экстремальные операции на трёх и более разных датах сохраняются как потенциально регулярный крупный спрос. Исключения доступны для просмотра. Это консервативная эвристика; для редких товаров нужна дополнительная проверка менеджером.
3. **Потерянный спрос:** только в явно переданных stockout-интервалах. Оценка по дням того же месяца и дня недели, при недостатке данных — по доступным дням в окне ±56 дней. Добавляется только положительная разница с фактической очищенной продажей. Будущие относительно даты расчёта продажи не используются.
4. **Сезонность:** средний дневной спрос полных месяцев; ранняя месячная сводка дополняет только месяцы до начала детализации. При наличии минимум 18 полных месяцев удаляется линейный тренд и оцениваются медианные месячные коэффициенты. Неполный сентябрь не участвует в расчёте месячных коэффициентов. Последние 90 календарных дней детализации используются для текущего уровня с учётом числа дней.
5. **Рост:** сравниваются последние 3 полных месяца с предыдущими 3 после сезонной корректировки. Тренд применяется, если все три месяца устойчиво выше/ниже базы на 5%; коэффициент ограничен диапазоном 0.5–2 и экстраполируется через квадратный корень, поскольку текущий уровень уже включает часть роста. Заданный `growth_pct` **заменяет** этот коэффициент, а не умножается на него повторно.
6. **Заказ:** `max(0, прогноз за lead_days + review_days + страховой запас − доступный остаток − поступления в горизонте)`. Просроченное неполученное поступление автоматически не вычитается. Отдельно моделируется дневной баланс, чтобы поздняя поставка не скрывала ранний дефицит. Если заказ равен нулю, но до поставки возникает дефицит, нужен перенос/ускорение поступления.
7. **Единицы:** потребность делится на `purchase_factor`, затем применяется минимальная партия `moq` и округление вверх до `pack`. Нулевая потребность остаётся нулём. MOQ и кратность заданы в единицах закупки; их перевод необходимо подтвердить для реальных кабелей.

Прогноз не является обученной нейросетью. Это воспроизводимая статистическая модель с устойчивыми правилами. Внешний LLM не нужен для расчёта или объяснений. Экономический эффект и точность на будущих реальных продажах не заявляются без отдельного измерения.

## CSV-интерфейс

Скачайте пример из приложения либо используйте `data/demo/`. Кодировка UTF-8, разделитель запятая, даты ISO `YYYY-MM-DD`; коды 1С и артикулы — строки.

| Файл | Поля |
|---|---|
| `products.csv` | `supplier, sku, name, stock, category, lead_days, review_days, unit, moq, pack, purchase_factor`; дополнительно `article, purchase_unit, stock_date, growth_pct, assumptions` |
| `sales.csv` | `supplier, sku, date, qty`; дополнительно `document, client_id, warehouse` |
| `incoming.csv` | `supplier, sku, eta, qty` — количество в складских единицах |
| `stockouts.csv` | `supplier, sku, start, end` — обе границы включены |
| `monthly_sales.csv` | Необязательно: `supplier, sku, month, qty`; `month` — первое число месяца, ранние месяцы дополняют сезонность |

`products.csv` и `sales.csv` обязательны. Пустой `stock` означает неизвестное значение и блокирует заказ. Пустой `growth_pct` включает автоматический тренд; 0 означает явно нулевую корректировку роста. Дополнительная загрузка `incoming.csv`/`stockouts.csv` через параметры полностью заменяет этот источник.

Выход содержит рекомендуемое и утверждённое количество, поставщика, код, артикул, складские/закупочные единицы, прогноз, страховой запас, поступления, дату риска, объяснение, ответственного и время утверждения. Формулы из импортированных текстов экранируются при экспорте.

## Тесты

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest -q
```

Тесты покрывают чувствительность к источникам, сезонность/тренд, stockout, разовые и повторяющиеся крупные операции, дату поступления, возвраты, неизвестные остатки, MOQ/кратность/единицы, CSV roundtrip, утверждение и экспорт. UI проверяется через Streamlit AppTest.

Проверено в среде разработки: **24 теста прошли**. Установка зависимостей не имеет конфликтов (`pip check`). Запуск на другом физическом ноутбуке и Docker остаются отдельными проверками команды; их выполнение не заявляется.

Повторная генерация синтетических CSV: `python -m scripts.generate_demo`. Локальная проверка архивов без копирования в репозиторий: `python -m scripts.check_real_data "путь/IEK.zip" "путь/Systeme electric.zip"`.
