# Axioma — объяснимое пополнение склада при неполных данных

**Для менеджера закупок Электрокомплект.** Обучаем общую модель спроса на истории товаров и превращаем шесть Excel-отчётов поставщика в проверяемый проект заказа: сезонный спрос, устойчивый рост, разовые покупки, остатки, ожидаемые поставки и ограничения отгрузки участвуют в одном расчёте.

Проблема: ручной расчёт занимает время, а одна большая продажа может завысить регулярную потребность. Решение: отделяем типичный спрос от всплесков и показываем, почему рекомендовано именно такое количество. Менеджер проверяет и выгружает заказ; автоматической отправки нет.

## Что показать жюри за 3 минуты

1. Запустить приложение без ключей и файлов компании: синтетическое демо полностью встроено.
2. Открыть «Сравнение методов», рассчитать сравнение. Увидеть по каждому товару, как меняется заказ без фильтра разовых покупок.
3. Нажать «Проверить прогноз на истории»: получить ошибки на трёх отложенных месяцах, сравнение с обычным средним и выгрузку результатов.
4. Загрузить IEK. Даже при неизвестном остатке виден **порог пополнения**: ниже какого количества запас нужно пополнять. Выбрать сценарий остатка и открыть его происхождение.
5. Показать объяснение одной рекомендации, кратность, ожидаемые поставки и Excel после ручной проверки.

## Отличительная идея: решение вместе с происхождением данных

Мы не выдаём неизвестный остаток за ноль. Для каждого товара можно получить порог пополнения независимо от текущего остатка, а при наличии месячного снимка — два явно обозначенных сценария. В расчёте сохраняются дата снимка, исходный остаток и продажи после него. Это позволяет работать с предоставленными файлами сразу, не ожидая ответа владельца кейса, и понимать, какие решения зависят от допущений.

Сценарии не восстанавливают неизвестные поступления, резервы и клиентов. Они превращают нехватку данных в прозрачное условное решение, которое менеджер может проверить. Выгрузка помечает сценарные позиции.

Это работающий прототип с частичным покрытием требований на реальных данных, а не заявленные «100% готовности». Коммерческая экономия, промышленное внедрение и победа в конкурсе не заявляются.

python3 -m venv .venv

Настройки безопасности PowerShell менять не требуется: если скрипты запрещены, используйте команды выше.

## Импорт реальных данных

Режим «Файлы поставщика»: выбрать IEK или Systeme Electric, загрузить соответствующий ZIP целиком либо все шесть XLSX. Не загружайте архив и его содержимое одновременно. ZIP читается в памяти, пути из архива не извлекаются на диск. Тип таблицы определяется по заголовкам, повреждённая кодировка имени файла не мешает. Ключ объединения — строковый код 1С. Артикул поставщика сохраняется отдельно.

| Источник | Использование |
|---|---|
| Детальные продажи | Дата, Номер, Документ, Код, Номенклатура, Ед., Склад, Количество; опционально client_id |
| Месячные продажи | Натуральный спрос по месяцам |
| Месячные остатки | Снимки; не точная длительность отсутствия |
| Путь IEK | Количества и даты поступления из заголовков |
| Путь Systeme Electric | Сводка, текущий свободный остаток, категории, поступление |
| MOQ | IEK — минимальная отгрузка; Systeme Electric — кратность |
| Сезонность | Готовая колонка СЕЗОННОСТЬ как профиль поставщика |

Продажи из отдельного месячного отчёта имеют приоритет перед сводкой. Детализация используется для поиска выбросов и заполнения только отсутствующих пар SKU/месяц; два представления одних продаж не суммируются. Складская детализация пока агрегируется по поставщику, отдельный склад не выбирается.

Опциональная переменная `AXIOMA_DATA_DIR` — локальная папка с подпапками `IEK` и `Systeme electric`. При её установке появляется кнопка открытия предоставленных локальных файлов. По умолчанию папки не читаются. Это настройка только локального запуска.

### Дополнительные CSV

Актуальные остатки и правила можно редактировать на странице или загрузить:

```csv
sku,stock,category,pack,moq
DEMO-001,25,1,10,1
```

Обязательны sku и stock. pack — кратность в единицах учёта, moq — минимум. Коды хранить текстом. Периоды отсутствия:

DEMO-004,2026-07-01,2026-07-20

Обе границы включены. Пересекающиеся периоды объединяются по дням.

## Методология расчёта

По умолчанию выбрана общая ML-модель: HistGradientBoosting с пуассоновской функцией потерь, нормированными лагами и календарными признаками. Прогноз усредняется с локальным средним, чтобы ограничить нестабильность. При менее 200 обучающих примерах включается статистический автовыбор. Шесть последних месяцев без положительного скорректированного спроса блокируют автоматическое возрождение спроса общей моделью.

Автовыбор сравнивает средние за 3/6/12 месяцев, экспоненциальное сглаживание, затухающий тренд, сезонные аналоги и Croston–SBA/TSB для редкого спроса. Выбор делается по последним шести месяцам внутри доступной истории, до внешних проверочных месяцев. Близкие результаты усредняются.

Подробности и мировые источники: [docs/methodology.md](docs/methodology.md). Ниже описаны общая обработка данных и исходная эвристическая модель, сохранённая для сравнения.

1. Используются завершённые месяцы до даты расчёта; неполный текущий месяц исключён также из обучения порогов выбросов. Для товаров без месячного отчёта история собирается из накладных; при наличии месячного отчёта накладные не добавляются к нему повторно. Отрицательные количества сохраняются как корректировки; отрицательный спрос не прогнозируется.
2. Строки накладной по товару и дню объединяются. При минимум 8 положительных наблюдениях порог выброса — `max(5 × median, Q3 + 3 × IQR, 1)`. Подозрительный объём заменяется медианой. При client_id дополнительно проверяется суммарная покупка клиента за день, включая несколько накладных. Крупные покупки известного клиента в три и более разных дня сохраняются как повторяющийся спрос. Это эвристика, а не обученный классификатор; менеджер может проверить исходный и исключённый объём.
3. Исключённый объём вычитается из месячного итога. Без детализации доступно консервативное сравнение с минимум двумя предыдущими одноимёнными месяцами.
4. Для известных stockout-дней продажи масштабируются на полный месяц по дням наличия. Для целого месяца отсутствия берётся медианный дневной спрос соседних месяцев. Отдельное явно включаемое приближение по нулевому месячному снимку заменяет заниженный спрос медианой, не заявляя точных дней отсутствия. Пустой остаток не считается нулевым.
5. Сезонность SKU оценивается по полным годам дневных продаж. При готовом профиле поставщика смесь: 80% SKU + 20% поставщик; при короткой истории — профиль поставщика. Коэффициенты ограничены и нормированы к среднему 1. Это допущение: денежная сезонность поставщика не равна натуральной сезонности каждого SKU.
6. База — средний очищенный и десезонализированный дневной спрос последних 6 месяцев. Тренд — отношение последних 3 месяцев к предыдущим 3, ограниченное −50…+100%. Если включён переключатель применения роста из сводки и передан `Кэф. Роста`, он имеет приоритет и заменяет исторический тренд (доля: 0.2 = +20%, предел −90…+300%). Это исключает двойное умножение на два тренда. Дополнительный прирост задаёт пользователь. Будущий спрос учитывает календарную сезонность. Источник прироста отображается в объяснении и экспорте.
7. `Период = срок новой поставки + интервал пересмотра`. `Цель = спрос периода + дневной спрос × страховые дни × множитель категории`.
8. Вычитаются свободный остаток и ожидаемые поступления с известной датой внутри периода. Неизвестные/просроченные поступления требуют уточнения; поздние показываются отдельно. Дефицит до новой поставки проверяется по дням.
9. Положительный заказ доводится до MOQ и округляется вверх по кратности. При нулевой потребности MOQ не создаёт заказ. Неизвестный текущий остаток блокирует безусловное количество заказа, но сохраняет порог пополнения. Для сценарного количества можно явно выбрать допущение по снимку.

21 день поставки, 14 дней пересмотра, 7 страховых дней — видимые стартовые допущения, не условия поставщиков. Множители категорий по умолчанию 1: смысл кодов категорий нужно согласовать и настроить.

## Архитектура

- `app.py`: Streamlit, настройки, ручное утверждение, Excel-экспорт.
- `src/data.py`: адаптеры Pandas/OpenPyXL, генерация синтетического демо.
- `src/engine.py`: детерминированный расчёт NumPy/Pandas, аномалии, объяснения.
- `src/scenarios.py`: сценарные остатки с происхождением данных.
- `src/validation.py`: проверка прогноза на отложенных месяцах.
- `src/forecasting.py`: статистические кандидаты и выбор по истории.
- `src/pooled.py`: общая модель градиентного бустинга.
- `src/orders.py`: проверка и объединение утверждённых заказов.
- `tests/`: pytest, Streamlit AppTest.

Данные и кэш находятся в памяти процесса. Утверждение сохраняется только в текущей сессии и скачанном файле. Базы истории, многопользовательской авторизации и промышленной защиты сервера нет; прототип предназначен для локального запуска.

## Соответствие кейсу и ограничения

| Требование | Реализация и граница |
|---|---|
| Базовая потребность | Шесть видов файлов, текущий свободный остаток, путь, настраиваемые категории/прирост |
| Сезонность и рост | Профили SKU/поставщика, тренд, видимые переключатели |
| Упущенный спрос | CSV подтверждённых периодов; отдельно отмеченное приближение |
| Разовые продажи | По накладной; при client_id — по клиенту за день |
| Заказы по поставщикам | Контекст выбранного поставщика, объяснение каждой позиции, Excel |
| MOQ | Минимум и кратность; единицы требуют согласования |

В предоставленной детализации нет ID клиента: номер накладной его не заменяет. Точных ежедневных stockout-периодов нет. Для IEK отсутствует актуальный свободный остаток: доступны порог пополнения и явно помеченные сценарии по снимкам; фактический остаток можно ввести отдельно. В сводке Systeme Electric текущий остаток есть лишь для части каталога.

Кабель может закупаться бухтами и учитываться метрами: нужно задать кратность в единицах учёта, автоматического справочника конвертации нет. Пустое значение месячных продаж трактуется как ноль, пустой остаток — как неизвестный.

Есть воспроизводимая историческая проверка всех товаров с минимум шестью месяцами истории до июня 2026 (см. ниже). Нет экономической оптимизации, гарантированного уровня сервиса, цены и суммы заказа, прямой интеграции с 1С. Excel — обменный формат, совместимость с конкретным загрузчиком 1С не заявляется. Заказы одного клиента между разными днями отдельно не объединяются.

### Сценарии при отсутствии текущего остатка IEK

В интерфейсе после загрузки файлов можно выбрать один из двух сценариев: сохранить последний известный начальный остаток или вычесть из него фактические продажи до даты расчёта, предполагая отсутствие поступлений и резервов. Для списания используются исходные продажи, включая крупные покупки и отрицательные корректировки. Будущие снимки и операции на дату расчёта и позже исключены. Отрицательная оценка обрезается до нуля. Это сценарии, а не точные остатки и не доверительный интервал. Без снимка заказ остаётся заблокированным; сценарий списания требует записей продаж товара после снимка. Известный свободный остаток не заменяется.

Источник, дата снимка и использованные продажи видны в таблице и выгрузке. Перед выгрузкой утверждённых сценарных позиций требуется отметить понимание допущения. Вкладка «Сравнение методов» показывает по каждому SKU влияние фильтра всплесков и отличие от среднего спроса за 6 месяцев. Это не backtest и не доказательство экономии; денежные эффекты без цен не заявляются.

## Воспроизводимая проверка качества

```bash
python scripts/validate_history.py
python scripts/validate_history.py --folder "/путь/к/IEK" --supplier IEK --limit 5000 --pooled
python scripts/validate_history.py --folder "/путь/к/Systeme electric" --supplier "Systeme Electric" --limit 5000 --pooled
```

Проверяются июнь, июль и август 2026 (в интерфейсе — последние три завершённых месяца перед выбранной датой). Для каждого месяца модель обучается только на более ранней истории. Выбираются первые 30 кодов в строковой сортировке с минимум шестью месяцами истории до первого проверяемого месяца. Выбор не использует будущий результат. Увеличить охват CLI: `--limit 5000`.

Готовая сезонность поставщика исключена: дата её построения неизвестна. Ретроспективные периоды отсутствия также исключены. Проверяем прогноз, а не текущие остатки или сумму заказа. Для каждого SKU считаем WAPE; среднее этих ошибок даёт одинаковый вес товарам без сложения метров, штук и других единиц. Нулевой суммарный факт исключается из процентной метрики, отсутствие целевой записи не считается нулём. Фактические продажи могут быть ограничены дефицитом и включать проектные покупки: это не наблюдение «истинного регулярного спроса».

Ограниченные выборки этих месяцев использовались при разработке для сравнения подходов, поэтому результат не является полностью независимым финальным тестом. В каждом отдельном прогнозе целевой и будущие месяцы исключены из обучения. Для внешнего подтверждения нужен новый временной период. Не скрываем случаи, где простой метод лучше. Результаты синтетического демо не выдаются за реальную экономию. Детали проверки: [docs/validation.md](docs/validation.md).

## GitHub и отправка решения — разные действия

- Commit сохраняет изменения локально; **Push отправляет их на GitHub**, где виден прогресс команды.
- Ссылка на официальный репозиторий не меняется при новых коммитах. До дедлайна код можно обновлять.
- «Изменить решение» на платформе меняет карточку проекта; это не загрузка каждой новой версии кода.
- Рабочие ветки сохраняют вклад участников отдельно. Перед финальной проверкой команды изменения должны быть объединены в `main`, затем повторно проверены и отправлены через Push.
- Не делаем пустые коммиты ради видимости работы. Значимые этапы фиксируются реальными изменениями и тестами. Каждый участник сохраняет свой вклад со своего аккаунта.

Развёрнутого публичного сервиса пока нет. `localhost:8501` доступен только на компьютере запуска, не является ссылкой для удалённого жюри. Установка выше позволяет повторить демо локально.

Результаты по всему подходящему каталогу и ограничения метрик: [отчёт проверки](docs/validation.md). В репозитории сохранены агрегированные JSON-отчёты; исходные коммерческие данные не публикуются.

## Проверка предоставленных архивов

Команда для локальной проверки всех файлов без публикации данных:

```bash
python verify_real.py "IEK.zip" "Systeme electric.zip"
```

Проверяются распознавание шести файлов на поставщика, уникальность кодов, наличие детализации, количество выходных строк, неотрицательность заказа, минимум и кратность. Итог сохраняется в `data/verification.json`; исходные данные и этот локальный отчёт исключены из Git.

## Дополнительный режим AXIOMA

Основной вход `app.py` и пакет `src/` сохраняют приложение команды. Дополнительная независимая реализация находится в `app_extended.py` и пакете `axioma/`: явный перевод единиц закупки (метры в бухты), утверждение с именем ответственного, CSV/XLSX и синтетические CSV-примеры. Режимы используют разные расчётные методики; результаты не складываются.

Запуск в том же окружении:

```bash
python -m streamlit run app_extended.py --server.port 8502
```

Методика и схема CSV: [дополнительный режим](docs/EXTENDED.md). Файлы `data/demo/*.csv` синтетические. `python -m pytest -q` проверяет обе реализации, включая оба интерфейса. Docker и `start.ps1` запускают основное приложение.
