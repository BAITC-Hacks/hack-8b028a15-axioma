# Защита Axioma · 3 минуты

## Перед выходом

Запустить `app.py`, открыть синтетический пример. Убедиться, что нет изменённых ручных настроек. На этом ноутбуке корпоративные ZIP доступны локально, но для короткого показа они не нужны. Держать открытым `docs/release-validation.md`. Полный backtest не запускать в первые минуты выступления.

## 0:00–0:25 — задача и результат

«Закупщик сводит Excel вручную. Крупная разовая продажа может завысить будущий заказ, а позднее поступление — скрыть дефицит внутри периода. Axioma превращает выгрузки в объяснимый заказ с проверкой менеджера».

## 0:25–1:05 — доверие к спросу

«Почему столько» → DEMO-001. Показать исходные продажи и всплеск 1500. Переключить фильтр, назвать изменение прогноза с экрана, вернуть фильтр. «Разовые продажи»: видны событие, основание и решение менеджера. Указать, что при расхождении накладных с месячной ведомостью автоматическое вычитание блокируется.

DEMO-004: включение компенсации подтверждённого отсутствия меняет спрос. У реальных архивов таких точных периодов нет; поддержан импорт и показан синтетический сценарий.

## 1:05–1:35 — заказ, который учитывает календарь

Показать дату дефицита и дневной баланс. «Если уже заказанное приедет поздно, простая сумма не поможет избежать промежуточного дефицита. Мы проверяем даты. То, чего не хватит до новой поставки, требует ускорения отдельно».

## 1:35–2:05 — законченный рабочий процесс

«Рекомендации» → «Проверить и утвердить заказ». Отметить строку, заполнить «Ответственный за утверждение», сохранить. «История» → сохранённый заказ → Excel. Показать общую корзину. «Исходный расчёт и решение сохраняются; пересчёт не переписывает утверждение».

## 2:05–2:40 — доказательства

«Проверка кейса» → запустить: 11 из 11 синтетических проверок для пяти обязательных требований. Открыть итоговый протокол: 3045 товаров, 18270 товаро-месяцев, семь методов. Основной режим уменьшил среднюю WAPE относительно среднего за шесть месяцев на 3,22% для IEK и 6,08% для Systeme Electric. Некоторые товары лучше у других методов. История использовалась при разработке; независимое подтверждение — на новом периоде».

## 2:40–3:00 — внедрение

«Следующий шаг — две недели параллельной работы с закупщиком. Нужны ежедневные остатки, ID клиента и согласованные сроки. Измеряем время, ручные исправления и дефицит. Деньги посчитаем по ценам и затратам; сейчас экономию не выдумываем».

## Дополнительный показ, если есть ещё минута

«Сценарии» → «Проверить остаток» → DEMO-002. Показать диапазон заказа и основание снимка. Ввести подтверждённый остаток 20, применить. В «Рекомендации» появляется рассчитанное количество, в истории сохраняется «Ручной пересчёт на 2026-09-23». У DEMO-005 без снимка сценарий не выдумывается. «Показать задержку на 7 дней» демонстрирует изменение срочности.

## Короткие ответы

- **Почему ошибка больше 100%?** Это отношение абсолютной ошибки к фактическим продажам по каждому товару. Редкие продажи дают большой процент. Показываем также медиану, нулевые товары и объёмную ошибку внутри каждой единицы.
- **Почему не одна нейросеть?** Выбор по прошлым данным воспроизводим, модели компактны. Общая ML-модель доступна и на части показателей лучше. Решение закупки включает ограничения и проверку человека.
- **Что с IEK без остатка?** Показываем порог пополнения; безусловный заказ блокируется. Можно заполнить CSV или явно принять сценарий по прошлому снимку.
- **Как отличаете клиента?** Только при наличии client_id; в данных кейса его нет. В реальных файлах анализируем накладные и повторяемость объёмов, клиентский случай проверен синтетически.
- **Отправляет ли заказ сама?** Нет. Сохраняет утверждённые строки и Excel; отправку контролирует закупщик.
- **Можно открыть по ссылке?** Код — в официальном GitHub. Демо запускается локально; публичный сервер не заявляем.
