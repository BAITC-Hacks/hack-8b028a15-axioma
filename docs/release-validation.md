# Проверка объединённой версии · 23 сентября 2026

**3 045 товаров, 18 270 пар товар/месяц, март–август 2026.** Семь методов проверены на одном составе товаров и неизменённых фактических продажах. Полные агрегаты: [release-benchmark.json](release-benchmark.json). Исходные таблицы, коды товаров и детальные результаты остаются локально.

На каждой исторической точке заново строятся очистка и прогноз, используя месяцы строго до целевого. Каталог отбирается по истории до марта, требуется минимум 12 наблюдаемых месяцев. При отсутствии целевой записи товар/месяц пропускается; явный ноль учитывается. Текущие сезонные коэффициенты поставщика, рост, остатки, ретроспективные периоды отсутствия и решения менеджера исключены. Текущие сроки поставки не участвуют: проверяется спрос за календарный месяц.

Основная метрика: для каждого SKU сумма абсолютных ошибок за шесть месяцев делится на сумму факта; затем берётся среднее по SKU с положительным фактом. Каждый товар имеет одинаковый вес. Медиана показывает типичный SKU, нулевой суммарный факт учитывается отдельно. Ошибка выше 100% возможна при нестабильном или редком спросе.

**Граница доказательства:** эта история использовалась при разработке, поэтому сравнение является диагностикой разработки, а не независимым финальным тестом. В каждой точке будущие месяцы исключены, но выбор алгоритма человеком учитывал эти результаты. Нужен новый временной период для внешнего подтверждения. Наблюдённые продажи включают проекты и могут быть ограничены отсутствием товара; истинный регулярный спрос не размечен. Денежный эффект не измерялся.

Основной режим — компактный автовыбор с очисткой и сверкой источников. «Автовыбор без очистки» позволяет увидеть вклад подготовки данных. Расширенный автовыбор и общая ML-модель команды сохранены рядом: не заявляем, что один метод выигрывает по всем показателям. Общая ML-модель имеет лучшую среднюю WAPE среди этих методов у IEK; расширенный автовыбор — у Systeme Electric. Это основание для дальнейшей проверки выбора метода на новых данных.

## Воспроизведение

```bash
python -m pip install -r requirements.txt
python benchmark.py "IEK.zip" --output data/benchmark-iek
python benchmark.py "Systeme electric.zip" --output data/benchmark-systeme
python verify_real.py "IEK.zip" "Systeme electric.zip"
python -m pytest -q
```

Файлы компании предоставляет владелец кейса. Без них команда `python benchmark.py` проверяет синтетическое демо. Параметры `--periods`, `--end`, `--max-skus` позволяют менять период и объём. Проверка всех товаров занимает несколько минут; время зависит от ноутбука и параллельной нагрузки.

## Проверка данных и рабочего процесса

Прочитаны все 12 XLSX: IEK — 3 184 товара и 171 603 строки детализации; Systeme Electric — 724 товара и 77 312 строк детализации. У IEK актуальные свободные остатки отсутствуют у всех 3 184 позиций. У Systeme Electric остаток известен у 497, неизвестен у 227. Неизвестный остаток блокирует безусловное количество заказа; доступен порог пополнения и явные сценарии по прошлому снимку.

За всю доступную историю обнаружены расхождения месячных итогов и накладных хотя бы в одном месяце у 1 075 SKU IEK и 471 SKU Systeme Electric. Причина расхождений неизвестна. Если отличие превышает max(1 единица, 2% месячного итога), вычитание аномалии из месячной ведомости блокируется, кандидат остаётся виден для сверки. Это защищает от повторного или несогласованного вычитания.

Встроенная «Проверка кейса» даёт 11 синтетических примеров для пяти обязательных требований. Тесты дополнительно проверяют современные модели, сохранение утверждения после новой сессии, сброс выбора после изменения расчёта, сценарное подтверждение, кратность и сроки поступлений. Утверждения хранятся локально в SQLite, привязаны к неизменяемому расчёту и ответственному; это журнал действий, а не электронная подпись.

## Окружение и воспроизводимость

Итоговая локальная проверка: Windows, Python 3.12, Streamlit 1.64, pandas 3.0.1, NumPy 2.3.5, scikit-learn 1.9.1. CI для Windows/Linux настроен в репозитории; локальный успех не является подтверждением запуска GitHub Actions. Docker-конфигурация сохранена, запуск контейнера в этой сессии не проверялся.

Отчёты `validation.md`, `extended-validation.md`, `final-verification.md` и `benchmark-*.json` фиксируют более ранние этапы или отдельный режим. Их числа нельзя смешивать с этим протоколом.

## Последнее объединение сценариев

**133 тестов пройдены** на Windows/Python 3.12. Дополнительно проверен полный путь: реальный парсер синтетического XLSX → неизвестный остаток → подтверждённый пересчёт → сохранённое утверждение → чтение итогового XLSX. Загрузчик и выбор строки эмулируются через AppTest; чтение/запись XLSX настоящие. В выгрузке проверены ответственный, ID расчёта/заказа, источник, кратность и сценарные допущения. Подтверждённый пересчёт сохраняется между сессиями только для той же даты и исходных файлов.

Новая сетка сценариев использует ту же политику дневного баланса, что и основной расчёт. Отдельная регрессия проверяет индивидуальный срок поставки товара. Прогнозные методы и исторические результаты выше при этом не менялись. В большом каталоге сценарии запускаются по кнопке; основной заказ доступен до этой дополнительной проверки.
